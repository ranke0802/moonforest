01 · 제가 이 프로젝트를 맡는다면

하나의 아트 방향, 여러 기기의 실행 예산

Babylon.js로 충분히 도전할 수 있는 목표다. 내가 맡는다면 엔진을 바꾸거나 자산을 계속 깎는 작업부터 하지 않는다. 같은 전투와 핵심 외형을 유지하는 공통 렌더 경로를 만들고, 저사양에서 확보한 여유를 대표 마법 한 개의 완성도에 먼저 사용한다.

조건을 명확히 한 가능성

구형 휴대폰의 안정적인 플레이와 PC의 높은 시각 품질은 함께 목표로 삼을 수 있다. 다만 모든 구형 기기에서 PC와 동일한 픽셀 수·이펙트 중첩·동시 보스 수로 60FPS를 보장할 수는 없다. 최소 지원 기능과 실제 전투 규모를 정하고, 핵심 실루엣·공격 예고·적중 표현은 공통으로 유지하는 설계가 필요하다.

공통으로 지킬 것

  • 플레이어·몬스터 실루엣, 승인된 모델·텍스처와 기존 LOD.
  • 정확한 공격 방향·범위·발동/명중 시점·제압 탈출·입력 반응.
  • 카툰·외곽선·내부선의 아트 정체성.
  • 주문 중심 형상, 이동 궤적, 명중 순간, 위험 표식.

기기별로 배분할 것

  • 장식 불씨·연기·먼지의 수와 겹침, 선택 잔광 수명.
  • 공용 블룸·왜곡·추가 반사 등 후처리.
  • 동시에 준비하는 자원 수와 메모리 예약.
  • 사용자가 선택하는 30/60FPS와 새로운 표현 프리셋. 기존 저장 설정은 몰래 바꾸지 않는다.

내 우선순위: 자원 선택/중복 정리 → 공통 준비·가시성 비용 통합 → 대표 마법 한 개와 아트 기준 장면 → 실제 전투 완주 → 콘텐츠 확장이다. 최적화와 그래픽 강화는 독립된 후보로 비교하며, 같은 패치에 섞어 개선 원인을 잃지 않는다.

02 · 출발점

이번 게임의 문제와 이미 갖춘 기반

관측/코드해석내가 바꿀 부분
PC 전사 원본 텍스처 추정 832MiB, 큰 두 장이 682.67MiB다운로드 파일이 작아도 GPU에서 큰 비압축 이미지로 상주한다. 모든 텍스처가 KTX2인 것은 아니다.PC도 실제 기능을 확인해 8K 압축 프로필을 선택할 수 있게 한다. 원본과 후보의 색공간·mip·품질을 비교한다.
기존 머리·피부 공용 8K가 137삼각형에 참조현재 새 머리카락 4K·얼굴 2K와 별도이며 실제 참조는 남아 있다.사용 UV 화소를 측정해 원본 화소 밀도 그대로 잘라 쓰거나 재배치한다. 이름만 보고 삭제하지 않는다.
최신 PC 로그 평균 CPU 4.48ms / 프레임 P95 24.4ms짧은 무전투 323프레임이다. 200ms 지연·S23 발열·늑대 전투 병목의 확정 근거가 아니다.평상시 비용과 준비·생성·사망 같은 순간 비용을 따로 다룬다. 기존 장시간 기록을 계속 사용한다.
인스턴싱·LOD·후보 레지스트리·월드 행렬 고정 이미 적용“인스턴싱 도입”만으로 새 개선안을 삼을 단계는 지났다.별도 시스템의 반복 후보/투영 계산과 자산별 준비 상태 검사를 공유한다.
검 잔상: 12구간 고정 버퍼, 상자: 96불꽃+256리본 고정 슬롯개별 효과의 재사용 기반은 있다.여러 효과가 동시에 커질 때의 전역 픽셀·동시 수·준비·메모리 계약을 추가한다.
지면 마법 aim()에서 지형 생성·절단·토폴로지 비교가 동기 실행보스별 캐시가 있어도 비싼 준비 과정은 캐시 적중 확인 전에 실행된다. 실제 시간은 미측정이다.공통 지형 자료·작업 배열 재사용과 준비 시점 분리를 우선 검토한다. 공격 예고와 실제 범위는 바꾸지 않는다.
배경·보스·이펙트가 각자 준비 예산을 가짐각각 1.5~3ms를 지켜도 같은 프레임에 겹치면 예산이 합산된다.한 프레임의 공유 준비 예산과 최고 메모리 예약을 적용한다.
그래픽이 아쉬운 이유에 대한 내 판단

높은 해상도 하나가 장면의 완성도를 만들지는 않는다. 지금은 명암·팔레트·지면/식생의 연결·빛 반응·효과 타이밍을 같은 아트 기준으로 묶는 작업이 필요하다. 이는 코드·과거 장면을 바탕으로 한 설계 판단이며, 새 그래픽이 완성됐다는 뜻은 아니다.

03 · 소유자 관점의 구조

기존 시스템을 버리지 않고, 여섯 개의 실행 계약을 추가

아래 이름은 제안하는 모듈 경계다. 현재 구현된 클래스처럼 해석하지 않는다. 기존 단일 scene·engine·게임 프레임과 검증된 자원 소유권을 유지한다.

플레이어·AI·충돌·피해→공유 포즈·풍경 정보→제한된 준비/효과 갱신→표면·선·그림자·선택 후처리
계약제안 모듈책임연결 방식
기기·표현 계약GraphicsProfile기능 지원·텍스처 포맷·효과 예산·명시적 사용자 선택을 하나의 계획으로 결정기존 render-policy / player-texture-profile을 감싼다. UA만 보고 성능 등급을 정하지 않는다.
자원 전체 수명AssetResidencyPlan공통·맵·배우·컷씬·이펙트·준비 중 자원의 공유 키, 소유자와 최고 메모리 예약기존 texture lifetime·캐시·ActorPopulation을 유지한다. CPU와 GPU, 다운로드 용량을 구분한다.
준비 작업 조정FrameWorkCoordinator로딩 필수·전투 즉시 시각·배경 준비·해제 작업의 우선순위와 한 프레임 공통 예산먼저 지오메트리 설치와 텍스처 교체 두 경로만 연결한다. 전투 시뮬레이션은 큐에 넣지 않는다.
풍경 재사용 정보SceneryViewSnapshot맵/카메라/편집 세대별 공간 후보·거리·화면 크기·준비 상태현재 공간 인덱스와 후보 레지스트리에서 만든다. 기존 LOD 선택 조건은 유지한다.
이펙트 실행EffectWorld필수/선택 레이어, 활성 슬롯·화면 면적·블렌드·업로드 예산과 생명주기검 잔상·상자 효과부터 어댑터로 연결한다. 새 Engine·RAF·효과별 타이머를 만들지 않는다.
공통 미술 환경VisualEnvironment아트 팔레트·명암·빛 방향·안개·시간/날씨·발광의 일관된 파라미터기존 카툰/하늘/조명 경로에 연결한다. 아트 변경은 최적화와 별도 검수한다.

가장 중요한 분리: 전투가 효과 준비를 기다리지 않게

게임플레이가 windup / release / impact / end / cancel 이벤트를 발행하고 이펙트는 이를 표현한다. 피해·판정·제압 상태는 현재 전투 시스템이 소유한다. 장식 효과의 풀 부족·준비 실패가 공격을 지연시키거나 보상을 취소해서는 안 된다. 필수 위험 표식은 사용 전에 준비하고 예산을 선점한다.

공용 준비 작업의 최소 데이터

{
  "owner": "map/actor/skill serial",
  "mapGeneration": "required",
  "priority": "loading-required | imminent-visual | scenery-prepare | cleanup",
  "estimatedPeakBytes": "separate CPU/GPU reservations",
  "readyDeadline": "optional known visual deadline",
  "cancel": "owned and idempotent",
  "publish": "only fully prepared result"
}

한 프레임의 공통 준비 예산은 처음에 약 1~2ms를 후보로 두고 기기별로 조정한다. 이는 JS 단계의 제안값이며, 단일 WebGL 호출의 긴 대기를 강제로 나누는 장치는 아니다. 로딩 화면에서는 별도 정책으로 필수 준비를 마친다. 필요한 지오메트리·텍스처 교체가 장식 준비 때문에 무한 대기하지 않게 우선순위와 대기 상한을 둔다.

04 · 구형 휴대폰부터 PC까지

기능 검사와 사용자 선택을 기준으로 분기

목표 프로필은 아래 세 가지로 시작한다. 숫자는 신규 VFX의 설계 시작 상한이며, 특정 기기 성능을 측정한 결과가 아니다. 필수 표현의 최악 조합을 미리 예약하고 선택 장식에 이 상한을 적용한다.

입자 수만으로 합격하지 않는다. 작은 불씨 1,000개보다 화면을 덮는 연기 20장이 비쌀 수 있다. 위 입자·draw 숫자는 모든 효과의 최적값도, 제한 안이면 안전하다는 보증도 아니다.

기능 선택 순서

  1. WebGL 기능, 텍스처 최대 크기·압축 형식·인스턴싱 등 실제 지원을 확인한다. OS/UA는 보조 정보로만 쓴다.
  2. 준비할 자산 프로필을 다운로드 전에 한 번 결정한다. 필요한 경우 기존 설정과 구분된 권장 프리셋을 제시한다.
  3. 일반 게임 프레임의 저비용 기록으로 여유를 본다. 계측 미지원 GPU 시간은 미확정으로 둔다.
  4. 새 이펙트의 선택 장식만 예산 안에서 안정적으로 배분한다. 현재 텍스처·LOD·화면 배율을 순간 FPS에 따라 몰래 낮추지 않는다.
  5. 최저 지원 기기/브라우저/동시 전투 규모는 출시 전 명시한다. 지원 불가 기능에는 작동하는 대체 표현이나 명확한 안내를 둔다.
해상도만 낮추면 메모리도 줄어드는 것은 아니다

현재 계산상 모바일 4K 압축 플레이어는 약 80MiB, 압축을 못 쓰는 2K RGBA 플레이어는 약 128MiB다. 기본 배경·추가 고해상도·이펙트·RTT·교체 중 메모리까지 합쳐 예산을 세워야 한다. 기존 배경 96/128/256MiB 예산은 추가 고해상도 텍스처만의 예산이므로 전체 GPU 예산으로 사용하지 않는다.

호환성은 WebGL 경로를 우선 유지한다. WebGL1까지 지원하려면 해당 SDK·커스텀 셰이더·인덱스·텍스처 경로를 따로 확인하고, GPU 파티클이 없어도 핵심 이펙트가 작동하도록 만든다. WebGPU는 상위 기기의 추가 경로 후보로 두고 최초 해결책으로 엔진 전체를 이관하지 않는다. Babylon은 두 경로를 병행 지원하지만, 선택은 앱에서 관리해야 한다. WebGL 지원 · WebGPU 지원.

05 · 화려한 마법의 설계

입자 수보다 형상·타이밍·명중 순간을 만든다

대표 마법 한 개를 예고 → 응축 → 빠른 방출 → 강한 명중 → 짧은 여운으로 완성한다. 색만 다른 작은 파티클을 많이 뿌리는 방식으로 그래픽 목표를 정하지 않는다.

1읽히는 예고범위·방향·문양
2큰 중심 형상덩어리·빛의 선
3속도 궤적리본·휘어지는 흐름
4명중의 절정섬광·링·방향 파편
5선택 여운연기·불씨·잔광

위 도표는 제작 방향 설명이다. 실제 게임에 적용된 효과 이미지나 비용 측정 결과가 아니다. 예고와 명중 시간은 각 스킬의 실제 게임 이벤트에 맞춘다.

레이어시각 목표가벼운 구현 방향품질/성능 규칙
필수 예고플레이어가 위험 범위·발동을 즉시 이해기존 지형 맞춤 지면 메시·공유 문양 아틀라스·단순 알파판정과 일치. 예산 부족으로 생략하거나 범위를 작게 보이지 않게 한다.
중심 형상불·얼음·번개가 서로 다른 덩어리와 움직임소수 메시·리본·플립북을 조합. 공유 버퍼에 인스턴스 데이터만 기록핵심 실루엣과 방향은 모든 프로필에서 유지한다.

06 · 실제 이펙트 비용 통제

화면 픽셀과 수명을 함께 관리

예산의 기준은 “몇 폴리곤인가”만이 아니다

3,600×2,084 화면은 약 750만 픽셀이다. 단순한 사각형 이펙트도 화면 절반을 덮는 4개 레이어라면 거칠게 약 1,500만 픽셀 상당의 겹침을 만들 수 있다. 깊이 가림·실제 셰이더·블렌드에 따라 실제 비용은 다르며, 이 값은 GPU 시간 측정이 아닌 작업량의 보수적 예다.

EffectWorld가 합산할 항목

  • 활성 효과·레이어·입자·메시 수와 공용 텍스처/버퍼 예약.
  • 보수적으로 투영한 화면 사각형 면적 × 레이어/패스 수. 모든 개별 입자를 정밀 투영하지 않고 효과 단위 bounds를 재사용한다.
  • 투명/가산/불투명 등 블렌드 계열, 재질·아틀라스 전환 수, 동적 버퍼 업로드 바이트.
  • 필수 위험·명중·탈출 표시와, 선택 장식의 중요도·거리·수명.
  • 현재 맵/시전 serial 소유권, 준비 deadline, 일시정지·사망·맵 이동·컷씬 종료의 취소 상태.

예산이 모자랄 때의 순서

  1. 필수 범위·방향·적중 표현을 먼저 예약한다. 해제/탈출 UI는 이 예산과도 독립적으로 유지한다.
  2. 중복되는 선택 불씨·연기·잔광을 묶거나 적게 발행한다. 현재 승인된 기존 효과를 임의로 축소해서 품질 유지 성과라고 보고하지 않는다.
  3. 우선순위가 낮고 오래된 장식만 먼저 반환한다. 같은 재질·아틀라스·블렌드 방식의 배치 안에서 슬롯을 재사용한다.
  4. 필수 표현조차 수용할 수 없는 장면은 콘텐츠 예산을 넘은 것으로 기록한다. 자동으로 피해·적 수·공격 시간을 바꿔 해결하지 않는다.

플립북은 테두리 여백·프레임 간 번짐을 검수하고, 빈 투명 영역을 과도하게 남기지 않는다. 빛나는 이펙트를 모두 실제 광원으로 만들지 않는다. 추가 동적 광원은 아주 제한된 공유 슬롯에서만 검토하고 그림자를 효과마다 추가하지 않는다.

3 · 플레이 가능한 대표 장면마을 출발→대평원 일반 몬스터 5+보스 1 전투→대표 마법→드롭/가방/퀘스트→짧은 파일 컷씬→복귀·저장20보스 동시 고품질 60FPS나 모든 기종 지원 완료로 확대하지 않는다.곰 샘플 컷씬 자동 추가 금지. 사용자가 승인할 실제 후보를 먼저 제공.

이 순서는 고정된 소요 시간 약속이 아니다. 각 교부는 직접 확인 가능한 결과 하나로 끝낸다. 첫 결과 전에 모든 조합의 장시간 자체 검수·아트 문서 작성에 매몰되지 않는다. 직접 관련된 필수 오류를 확인하고 결과를 전달한 뒤 필요한 회귀 범위를 확장한다.

10 · 현실적인 성능·품질 목표

최대 그래픽 옵션과 최소 지원 조건을 모두 정직하게

영역설계 목표/확인 방법중단·복구 기준
60FPS 여유시작 목표 CPU 정상 작업 P95 약 8~10ms, GPU P95 약 12~13ms 이하 검토. CPU/GPU는 겹쳐 실행되므로 합산하지 않는다.지금 PC의 323프레임/GPU 역사 값으로 S23 통과 처리하지 않는다.
새 마법 여유신규 VFX의 추가 GPU 비용은 표준 프로필에서 P95 약 2ms 안쪽을 첫 목표로 검토. 실제 GPU 계측이 없으면 미확정.입자 수만 제한했는데 투명 겹침·후처리 비용이 크면 표현 레이어를 다시 설계한다.
구형 기기 안정성최소 지원 기기/브라우저를 선정해 30FPS 프로필 완주부터 확인. 현재 사용자 60FPS 설정은 자동 변경하지 않는다.기능 미지원·메모리 부족을 검은 화면/무한 로딩으로 방치하지 않는다.
같은 핵심 표현필수 범위·방향·중심 형상·명중/탈출 메시지를 프로필 간 비교.저사양에서 위험 표식 누락, 과한 발광으로 적/전사가 안 보임, 장식 제거로 판정 인지가 달라지면 실패.
지속 프레임최종 후보에서 10분 단일 기록으로 P95/P99와 50/100/200ms 초과 횟수·원인 분리. 필요 시 기존 상세 옵션을 제한 사용.평균 FPS 하나로 완료하지 않는다. 단발 200ms를 전부 GPU/텍스처 탓으로 돌리지 않는다.
메모리·생명주기왕복/소환/사망/드롭/컷씬 후 같은 상태의 살아 있는 소유자·예약·풀 상한을 비교.숨은 효과·이전 맵·중복 프로필·이전 시전 객체가 남아 누적되면 해당 경로 롤백.
전투 동등성기존 입력·시간의 HP/타점/제압·탈출·피격·보상·저장 결과를 기존 검사로 확인.VFX 예산이 피해나 공격 시간을 바꾸거나 컷씬 취소 후 입력이 돌아오지 않으면 실패.
배포·자산 보존0.2 별도 후보·원본 등록·hash·가이드 반영. 0.1 동결과 기존 소스 보존.공유 리소스 그래프 덮어쓰기·원본 삭제·브라우저 자동조작으로 검수 범위를 확대하지 않는다.
가능성을 높이는 제작 원칙

같은 폴리곤 수로도 더 나은 화면을 만들 수 있고, 같은 명중감을 더 적은 효과 레이어로 표현할 수 있다. 이를 위해 화려한 마법을 나중에 무제한 추가하는 대신, 대표 마법과 실제 전투 장면을 먼저 완성하고 그 비용을 신규 콘텐츠의 준입 기준으로 삼는다.

11 · 최종 제안

내가 지금 선택할 실행안

이 코드베이스를 내가 맡는다면, 기존 렌더링 최적화를 유지한 채 자원 선택·공통 준비·전역 이펙트 계층을 먼저 정리하고, 대평원 전투 한 장면의 그래픽을 확실히 끌어올리겠다.

  1. 큰 텍스처: PC 8K 압축 후보를 빠르게 확인하고, 작은 UV 사용 영역의 낭비를 별도로 없앤다. 832→208MiB는 전사 텍스처의 계산 시나리오이며 전체 기기 RAM이나 FPS 개선율이 아니다.
  2. 렌더 준비: 풍경/소환/마법이 각자 준비 작업을 몰아서 하지 않게 한다. 필요한 이전 LOD와 정확한 판정은 유지한다.
  3. 이펙트: 중심 형상·타이밍·명중 플립북을 먼저 만들고, 장식량·공용 발광을 기기별로 배분한다.
  4. 아트: 인물·지면·식생·원경·빛·마법을 하나의 기준 장면에서 맞춘다. 단순한 고해상도나 더 많은 입자를 품질의 대체 지표로 삼지 않는다.
  5. 확장: 검증된 한 전투 장면의 비용 계약으로 몬스터·NPC·스킬·컷씬을 추가한다. 지원 기기별로 감당 가능한 동시 규모를 명시한다.
