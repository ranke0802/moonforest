MoonForest 0.3 · 성능 구조 진단 · 2026-11-22

객체를 하나씩 다루는 구조가 폰의 주 스레드를 막고 있다

근거: 배포본 8a77f78을 PC 브라우저에서 실행해 잰 장면 구조, 갤럭시 S23 성능 기록 be7ac85e(315초)·b21cc518(408초), 소스 ArcherPreview/src·src/v03 447개 모듈 전수 검색. 코드는 아직 바꾸지 않았다.

결론

  1. 폰이 막히는 곳은 GPU가 아니라 JS 주 스레드다. CPU가 느려진 상태의 평원(몬스터 19마리)에서 프레임 간격 24ms 중 계산이 20.1ms다. 해상도를 낮춰도 프레임이 오르지 않는 이유다.
  2. 원인은 기능 하나가 아니라 "객체 수 × 객체마다 하는 JS 처리"다. 평원 풍경 1,364개가 각자 노드를 가진 InstancedMesh이고(장면 노드 3,848개), 재질 125개 중 얼려 둔 것은 6개(5%)뿐이며, 몬스터마다 골격·동작 22세트·외곽선 껍질을 따로 갖는다. 매 프레임 이 개수만큼 고르기·준비 확인·바인딩을 한다.
  3. 같은 일을 하는 장치가 겹쳐 쌓였다. 그릴 대상을 정하는 장치 12종, 작업을 나누는 예산 장치 9종, 셰이더를 보관하는 장치 2종, 애니메이션 재생기 5종, 외곽선·잉크 3계통이 따로 돈다. 객체를 묶지 않고 개별로 둔 채 문제가 생길 때마다 거르는 장치를 덧댄 결과다.
  4. 일부 장치는 서로 효과를 지운다. 프레임당 2ms 준비 예산이 있어도 한 번에 40~114ms가 걸리는 셰이더 생성은 막지 못한다. 프레임 가드의 단계 일부는 품질 복구 기본값이 꺼 버린다.
  5. 처방은 덧대기가 아니라 줄이기다. 풍경을 thin instance 묶음으로 바꾸고, 재질을 얼리고 가벼운 툰 재질로 통일하고, 몬스터를 종 단위로 공유하면 겹친 장치 상당수가 필요 없어진다. 폰에서 프레임당 약 4~9ms를 줄일 것으로 추정한다(미검증).

4. 개선 여지와 Babylon 기능 대체

기대 효과는 PC 측정과 폰 기록 비율로 낸 추정치다. 적용 전후 폰 기록으로 확인해야 한다.

4-1. Babylon 기능으로 바꾸면 더 잘 동작하는 것

풍경 → thin instance 묶음

  • 지금: 배치 하나가 InstancedMesh 하나 + 부모 노드. 켜진 인스턴스마다 매 프레임 고르기·LOD·절두체 검사, 위치 버퍼 다시 올리기(폰 138회 1.24ms).
  • 바꿀 것: 원본 × 16m 칸 × LOD 단계마다 메시 하나에 thinInstanceSetBuffer('matrix', …, 16, true)로 고정 버퍼. 칸 단위로 켜고 끄고 LOD를 바꾼다. 나무 반투명·그림자 페이드는 thinInstanceRegisterAttribute로 인스턴스 값.
  • 없어지는 것: 후보 교체, LOD 유지, 칸 거르기의 개별 켜고 끄기, 부모 노드 1,300여 개, 프레임마다 버퍼 갱신.
  • 기대: 폰 고르기 4.3ms의 대부분과 버퍼 갱신 1.2ms → 프레임당 −2~4ms (추정)
  • 대가: LOD 전환이 칸 단위가 된다(칸 안의 먼 것과 가까운 것이 같은 단계). 칸을 작게 하거나 LOD 거리를 칸 기준으로 다시 맞춰야 한다. 관련 모듈(village-streamed-environment village-demand village-outlines)을 함께 고치는 큰 작업이다.

재질 얼리기 material.freeze()

  • Babylon은 얼린 재질의 준비 확인을 건너뛰고 재질 값 다시 바인딩도 생략한다(9.31 소스에서 확인).
  • 지금 125개 중 6개만 얼어 있다. 풍경·몬스터 본체처럼 값이 안 바뀌는 재질은 얼리고, 맞은 번쩍임·페이드처럼 값이 바뀌는 순간에만 풀거나 인스턴스 값으로 옮긴다.
  • 기대: 그리기 제출의 JS 부분 감소, 폰 −1.5~3ms (추정)
  • 위험: 프레임마다 값을 바꾸는 플러그인(동굴 안개, 맞은 번쩍임)이 멈춰 보일 수 있어 재질별로 확인이 필요하다.

툰 재질을 가벼운 바탕으로

  • 지금: 빛을 끈 PBRMaterial + 기본 부가 기능 6종 + 우리 플러그인. PBR은 Babylon에서 셰이더가 가장 크다.
  • 바꿀 것: StandardMaterial(빛 끔, 자체 발광 텍스처)에 지금의 MaterialPluginBase 플러그인을 그대로 옮기거나, 전용 ShaderMaterial 하나로 통일한다. 종마다 재질 설정을 맞추면 여러 종이 프로그램 하나를 같이 쓴다.
  • 기대: 종끼리 프로그램을 같이 쓰면 플레이 중 셰이더 생성 횟수가 종 수만큼 준다. 생성 한 번의 무게 차이는 아직 모른다: PC에서 PBR 프로그램은 7~8ms, 기본 재질 프로그램도 4~12ms가 걸렸다 (바탕 재질을 바꾸는 이득은 재 봐야 한다)
  • 위험: 그림이 달라질 수 있다. 바꾸기 전후 같은 장면을 화소 비교해야 한다.

먼 몬스터는 VAT

  • VertexAnimationBaker + BakedVertexAnimationManager: 종마다 동작을 텍스처 하나로 굽고 GPU가 재생한다. CLAUDE.md의 "많은 생물은 VAT" 규칙과 같다.
  • 가까운 몬스터·싸우는 몬스터만 지금 골격을 쓰고, 먼 것은 VAT로 바꾼다. 먼 몬스터의 CPU 샘플링·골격 준비·뼈 텍스처 올리기가 없어진다.
  • 기대: 몬스터 쪽 −1~2ms (추정)
  • 대가: VAT는 동작 사이 섞기가 없다. 먼 거리에서만 쓰면 눈에 띄기 어렵지만 비교 화면으로 확인해야 한다. 외곽선 껍질도 같은 VAT를 써야 한다.

몬스터 복제 가볍게

  • 자체 샘플러를 쓰는 늑대류는 복제 때 AnimationGroup을 만들 필요가 없다. 키 표와 보간 위치표를 종 단위로 공유하고 개체는 시간·혼합 상태만 갖게 한다(평원 AnimationGroup 460 → 30 안팎).
  • 기대: 복제·동작 준비 시간(폰 최대 16ms·57ms)과 메모리 감소 (추정)

길게 볼 것: WebGPU + 스냅샷 렌더링

  • Babylon 9의 WebGPUEngine은 그리기 명령을 묶어 두고 다시 쓰는 스냅샷 렌더링(snapshotRenderingMode)을 지원한다. 폰에서 막히는 그리기 제출 JS를 크게 줄이는 방법이다. Android Chrome은 WebGPU를 지원하지만, S23에서 직접 확인하지는 않았다.
  • 대가: 우리 GLSL 셰이더·플러그인·KTX2 경로를 모두 다시 검증해야 하는 전환이다. 위 작업 뒤에 따로 검토한다.

4-2. 우리 코드에서 합치거나 덜어낼 것

대상할 일이유
셰이더 보관 2종하나의 보관소로 합치고 상한을 하나로같은 방식의 중복. 앞으로 셰이더 문제를 볼 곳이 한 군데가 된다
작업 예산 9종준비 작업을 한 대기열로 모으고, 나눌 수 없는 큰 호출(셰이더·동작 준비)은 로딩 그림 뒤로 보낸다지금 예산은 작은 일만 나누고 큰 일은 못 막는다
그릴 대상 장치 12종thin instance 전환과 함께 칸 단위 판단 하나 + Babylon 절두체로 줄인다. GPU 가림 쿼리는 효과를 재서 남길지 정한다객체를 묶으면 개별 거르기가 필요 없다
애니메이션 재생기 5종자체 샘플러 하나(종 단위 공유 표, 상수 채널 처리 포함)로 합치고, 주인공처럼 섞기가 많은 경우만 AnimationGroup같은 일을 세 번 구현했다
프레임 가드 + 품질 복구하나의 품질 단계표로 합친다(기기 등급별 시작값 + 못 지킬 때 낮출 순서)같은 대상을 반대로 조절한다
진단가벼운 상시 계수(초당 합계)와 무거운 측정(엔진 감싸기·장면 계측)을 나누고, 폰 기록은 가벼운 쪽만 기본으로기록 수치에 측정 부하가 섞인다
꺼진 채 남은 것분할 올리기·원경 단순화·내부선의 기본 경로 비용 확인 후 정리코드 경로와 준비 작업이 남는다

4-3. 이미 잘 쓰고 있는 Babylon 기능

KTX2(UASTC), Meshopt, 뼈 텍스처, 병렬 셰이더 컴파일, skipPointerMovePicking, 복제·재질 메시 맵(useClonedMeshMap, useMaterialMeshMap), 행렬 동결(1,447개), instantiateModelsToScene. scene.performancePriority는 중간 단계가 화면 지우기 생략 정도라 이득이 작고, freezeActiveMeshes·옥트리는 카메라가 계속 움직이고 스트리밍하는 지금 구조에 맞지 않는다.

5. 권하는 순서

1단계 · 위험 낮음 — 재질 얼리기(값이 바뀌는 재질만 예외), 셰이더 보관 통합, 진단 측정 부하 분리. 화면은 그대로여야 하므로 전후 화소 비교로 확인하고 폰 기록 한 번.
2단계 · 가장 큰 작업 — 풍경을 thin instance 묶음으로 전환하고 그릴 대상 장치를 정리. 평원·마을 전후 화소 비교, 폰에서 고르기·그리기 제출 시간 비교.
3단계 · 끊김 — 몬스터 종 단위 공유(복제 가볍게), 가벼운 툰 재질로 통일, 처음 만드는 셰이더와 동작 준비를 로딩 그림 뒤로. 폰 기록의 플레이 중 셰이더 생성 횟수로 확인.
4단계 · 평균 프레임 마무리 — 먼 몬스터 VAT, 애니메이션 재생기 통합, 프레임 가드와 품질 복구 통합. 먼 몬스터는 비교 화면을 먼저 보여 드린다.

각 단계가 끝날 때 CLAUDE.md의 "적용된 최적화 대장"에서 필요 없어진 장치를 지우고, 새 장치를 넣을 때는 같은 범주 표를 먼저 본다.

6. 확인하지 못한 것

  • 기대 효과 수치는 모두 추정이다. 폰에서 적용 전후를 재야 한다.
  • 재질을 얼렸을 때와 툰 재질을 바꿨을 때 그림이 같은지는 아직 화소 비교하지 않았다.
  • 폰 기록에 섞인 측정 부하의 크기.
  • 폰 CPU가 2~3분 뒤 1.7배 느려지는 원인(발열·절전·충전 상태). 기록으로 가릴 수 없다.
  • GPU 가림 쿼리(village-occlusion)와 칸 거르기가 실제로 줄이는 양.
  • 평원 도착 직후 주인공 애니메이션 200ms 한 프레임의 원인.
